01なぜ複数のAIを混ぜるのか

AIモデルは失敗の仕方がそれぞれ違います。Claude は判断と構成が強い代わりに、自分で出した案を自分で壊しにくい。GPT は科学的な留保が正確な代わりに、着地とタイトルの磁石を弱める。Grok は X や Web の実測で既出との衝突を暴ける代わりに、社内の実測データを持たないので「何が当たるか」の判断を誤る。Gemini 3.8 Flash は日本語の話し言葉が自然で安価な代わりに、企画の判断は任せられない。

だから「ディレクター1人＋専門家3人」の体制にします。ディレクターは Claude Code（または Codex）上のメインモデルで、企画の採否・言い切りの強さ・タイトル・最終レビューという判断を持ちます。専門家には作業を渡し、結論は渡しません。

ディレクター
Claude Code / Codex のメインモデル

ヒアリング、企画の採否、構成、章ブリーフ、最終レビュー。他AIの出力を突合して決定メモを書く。

渡さない: 判断そのもの。他AIの結論をそのまま採用しない
Gemini 3.8 Flash
日本語本文の執筆・言い換え・校正修正

章ブリーフから本文を書く。校正ツールが指摘した文だけを直す。同じブリーフで比べたとき、素の出力がいちばん自然だった。

渡さない: 企画の判断、文長や語尾の数値縛り（付けると不自然になる）
GPT
科学的射程・論理の穴・一次資料

企画案の言い過ぎを検出し、既存動画への波及まで拾う。反証耐性の確認役。ChatGPT サブスク枠で動くので API 課金なし。

渡さない: タイトルと着地（磁石が弱くなる）。1応答5〜8分かかる前提で使う
Grok
市場の飽和度・X/Web のリアルタイム実測

「そのテーマは既に何本出ているか」「視聴者はどう反応しているか」を X 投稿と Web で実測し、容赦なく反論する。

渡さない: 勝ち型の判断。出してきた再生数は自分の実測と突合してから使う

02接続の3経路

他のAIを「参加させる」と言っても、やることは3つのどれかです。どの経路でも、ディレクター側は「スクリプトを叩いて、結果ファイルを読む」だけなので、Claude Code と Codex で手順は同じになります。

経路仕組み向いている相手準備
A. API を直接叩くPython の標準ライブラリだけで HTTP を投げる。同梱の gemini_chat.py / grok_consult.py がこれGemini・GrokAPI キーを1つ発行して環境変数に置く
B. CLI を呼ぶ相手のコマンドラインツールをサブプロセスで起動し、標準入力でプロンプトを渡す。gpt_consult.py がこれGPT（Codex CLI）・Claude（claude CLI）CLI をインストールしてログイン。API キー不要
C. MCP で登録する相手を MCP サーバーとして登録し、ディレクターが「ツール」として直接呼ぶGPT（codex mcp-server）1行の登録コマンド。ツール一覧に出る

迷ったら A と B で十分です。C は「Claude が自分の判断で GPT を呼びに行く」動きが欲しいときに足します。

03Gemini 3.8 Flash を参加させる

本命です。日本語の本文執筆と校正修正を Gemini に任せると、Claude 側は判断とレビューに集中でき、従量課金も下がります。

3-1. API キーを発行する

  1. Google AI Studio を Google アカウントで開き、左下の Get API key → Create API key。
  2. キーは AIza… で始まる文字列。発行直後にコピーして、パスワードマネージャーに控えます。
  3. Billing で前払いクレジットをチャージします。残高が 0 になるとどのモデルも 429 prepayment credits are depleted で止まるので、最初に少額を入れておきます。

3-2. キーを置く

同梱スクリプトは 環境変数 → 設定ファイル の順で読みます。どちらか片方でかまいません。

# 方法1: シェルの環境変数（~/.zshrc に追記）
export GEMINI_API_KEY="AIza..."

# 方法2: 設定ファイル（~/.config/clbs/config.toml）
mkdir -p ~/.config/clbs
cat > ~/.config/clbs/config.toml <<'EOF'
[gemini]
api_key = "AIza..."
EOF

Claude Code で常時使うなら、~/.claude/settings.json の env に入れておくとセッションごとの設定が不要です。

{ "env": { "GEMINI_API_KEY": "AIza..." } }
キーの扱い

キーはチャットに貼らない。Git にコミットしない（~/.config/clbs/ はリポジトリの外）。AI に「キーを設定して」と頼むときも、AI に値を渡さず自分でファイルに書きます。

3-3. 動作確認

# スキルを入れていれば scripts/ にある（Codex は ~/.codex/skills/…）
cd ~/.claude/skills/clbs-youtube-script-pro
python3 scripts/gemini_chat.py --list | grep 3.8       # gemini-3.8-flash が出ればOK
python3 scripts/gemini_chat.py -p "「今日は天気がいいですね」を友達に話す口調で1文に。答えだけ"
# → 今日いい天気だね！   [tokens] in=28 out=6 model=gemini-3.8-flash

これで接続は完了です。gemini_chat.py は 90 行ほどの Python で、追加インストールは要りません。

3-4. Claude Code に「Gemini に書かせろ」と指示する

スキル（clbs-youtube-script-pro v2）には既に「本文執筆と校正修正は Gemini に振れる」手順が入っています。あとはチャットで役割を宣言するだけです。

Claude Code に貼る
この台本プロジェクトでは役割を分けます。
- あなた（Claude）: ヒアリング、企画3案、構成、章ごとのブリーフ作成、最終レビュー
- Gemini 3.8 Flash: 本文の執筆と、校正ツールが指摘した文の修正
  （scripts/gemini_chat.py と scripts/ja_style_fix.py を使う。GEMINI_API_KEY は設定済み）

章ブリーフには、企画・語り手・章の位置・使う素材と順序・断定ライン・タグ形式・
「1行1文」を書き、文長や語尾の数値縛りは入れないでください。
Gemini の出力は scripts/qa_script.py で検査し、FAIL は ja_style_fix.py で該当文だけ直し、
--strict で PASS してから私に見せてください。

ブリーフを Gemini に渡すコマンドは次の形です。システム指示に文体ルール（references/japanese_style.md）を渡すのがコツで、これを付けるだけで「AIっぽい前置き」と「和訳調」がかなり減ります。

python3 scripts/gemini_chat.py -f briefs/ch3.md \
  --system references/japanese_style.md -o draft/ch3.txt

3-5. 校正ゲートと修正パス

書けた本文は機械検査に通します。禁止フレーズ（「結論から言うと」など）、許可取り（「〜させてください」）、AI記号（**・——）、英文和訳調（受け身で行為者を隠す／名詞化／冗長な強調／「〜ですね」で言い切りを弱める）、演出比喩、タグ規約違反を拾います。

# 検査（FAIL があると exit 1。--strict で和訳調も FAIL 扱い）
python3 scripts/qa_script.py videos/20260917_xxx/ --strict

# 指摘された文だけ Gemini に直させて元の位置に戻す（タグ・break は不変）
python3 scripts/ja_style_fix.py videos/20260917_xxx/script.txt --strict
# 修正前: FAIL 4 / WARN 1  文数 9  対象 9文
# 修正後: PASS FAIL 0 / WARN 0  差し替え 9文  タグ/break保持 OK
直す単位は文

ja_style_fix.py は指摘された文だけを番号付きで送り、直した文を JSON で受け取って差し戻します。全文の書き直しをさせないので、事実や構成が勝手に変わりません。修正前のファイルは .bak_日時 に残ります。

機械が消したがるもの

「Aではなく、実はB」の常識破壊の対比や、「〜かもしれません」の誠実な留保は、校正ツールが消したがります。直すか残すかはディレクターが判断し、消えていたら戻してください。

3-6. Codex から使う

Codex でも同じスクリプトを叩くだけです。毎回説明しなくて済むように、プロジェクト直下の AGENTS.md に役割を書いておきます（Codex は起動時にこれを自動で読みます）。

# AGENTS.md（プロジェクト直下）
## 台本制作の役割分担
- 本文の執筆・校正修正は Gemini 3.8 Flash に任せる:
  ~/.codex/skills/clbs-youtube-script-pro/scripts/gemini_chat.py
  ~/.codex/skills/clbs-youtube-script-pro/scripts/ja_style_fix.py
- 納品前に scripts/qa_script.py <project> --strict が PASS であること

3-7. コストと落とし穴

コスト
Flash 系は安価です。校正パス1回（60文まとめて送信）で入力約2,000トークン・出力約150トークン。台本1本の執筆＋校正で数十円のオーダーになります。
数値縛りを付けない
「1文30字以内」「〜んです は5文に1回」のような制約をブリーフに入れると不自然になります（同一ブリーフ比較で本人判断済み）。文体は --system のルールで寄せ、数値では縛らない。
タグを壊さない
章ごとに書き直させるときは、演出タグの行数と順序が元と一致するか必ず検証します。ja_style_fix.py はタグと break を触らない設計なので、この問題が出ません。
モデル名
gemini-3.8-flash。名前が違うと 404 になるので --list で確認。

04GPT を参加させる（Codex CLI 経由・API課金なし）

ChatGPT の有料プラン（Plus / Pro / Business）があれば、Codex CLI を通して GPT を呼べます。API キーは要らず、サブスクの枠内で動きます。

4-1. Codex CLI を入れてログイン

brew install --cask codex          # Windows は WSL2 上で npm install -g @openai/codex
codex login                        # ブラウザが開くので ChatGPT でログイン
codex login status                 # "Logged in using ChatGPT" が出ればOK

4-2. 経路B: スクリプトから呼ぶ（相談用・おすすめ）

プロンプトを標準入力で渡し、応答を Markdown で保存します。reply で同じセッションを続けられるので、R1 → R2 の多ターン相談ができます。

cd ~/.claude/skills/clbs-youtube-script-pro
python3 scripts/gpt_consult.py ask   --out _gen/gpt --name plan -f brief.md --model gpt-6-astra
python3 scripts/gpt_consult.py reply --out _gen/gpt --name plan -f decision_v1.md
# → _gen/gpt/plan_r1.md, plan_r2.md（応答）/ plan_prompt_rN.md（送った質問）
プロンプトは必ず標準入力から

codex exec "長いプロンプト" と引数で渡すと「Reading additional input from stdin」で止まります。スクリプトは - を付けて stdin から渡しています。手で叩くときも codex exec --model gpt-6-astra - < prompt.md の形にします。

利用できるモデル名はプランで変わります。--model を省くと ~/.codex/config.toml の既定モデルが使われるので、まずは省略で試してください。

4-3. 経路C: MCP として Claude Code に登録する

Claude が「ツール」として GPT を直接呼べるようにします。Claude が自分の判断で Codex に実装を委譲する、といった使い方が可能になります。

claude mcp add -s user codex -- codex mcp-server
claude mcp list        # codex: codex mcp-server - ✓ Connected

Claude デスクトップアプリで /mcp に出ないときは、~/Library/Application Support/Claude/claude_desktop_config.json に直接書く方法もあります。

{ "mcpServers": { "codex": { "command": "/opt/homebrew/bin/codex", "args": ["mcp-server"] } } }

登録後は Claude に「codex ツールで GPT に反論させて」と言えば呼び出せます。モデルを指定したいときは model: "gpt-6-astra" のようにツール引数で渡します。

brew で Codex を更新したら Claude Code を再起動

codex mcp-server のプロセスは起動時のバイナリを掴み続けます。更新後にセッションを再起動しないと「requires a newer version」の 400 エラーになります。

4-4. GPT に何を聞くか

  • 企画案の主張で「言い過ぎ」になっている箇所と、一次資料に基づく言える上限
  • この構成に対する、物理学者・専門家・懐疑派からの未解消の反論と、台本内で先回りする応答方針
  • 既に公開している動画との矛盾（波及の検出）

タイトルや着地は聞かない。GPT は留保を付けて弱める方向に寄るので、そこはディレクターが決めます。

05Grok を参加させる（xAI API）

Grok の強みは X 投稿と Web をその場で検索して、引用 URL 付きで返すことです。企画の「既出との衝突」「視聴者の生の反応」を実測する役に使います。X Premium のサブスクと API 課金は別建てで、API は console.x.ai でクレジットを買って使います。

5-1. キーを発行して置く

# console.x.ai → API Keys → Create（先にクレジットを購入）
export XAI_API_KEY="xai-..."
# または ~/.config/clbs/config.toml に [xai] api_key = "xai-..."
python3 scripts/grok_consult.py --list      # grok-4.6 などが出ればOK

5-2. 相談とリサーチ

# 企画相談（検索なし）。reply で同じセッションを継続
python3 scripts/grok_consult.py ask   --out _gen/grok --name plan -f brief.md
python3 scripts/grok_consult.py reply --out _gen/grok --name plan -f decision_v1.md

# X + Web を検索して実測（引用URL付き）
python3 scripts/grok_consult.py research --out _gen/grok --name market \
  -f query.md --search both --from-date 2026-08-01
# → _gen/grok/market_r1.md の末尾に「## 引用」としてURL一覧
reasoning は medium
既定の high だと推論が出力予算を食い、「以下に整理します」と予告だけで終わることがあります。スクリプトは medium を既定にし、本文が短いときは同じセッションで続きを書かせます。
R2 は reply で
文脈を ask に貼り直すと入力が20万トークンを超えて単価が2倍になります。
コスト
実測で、X検索8回のリサーチ1回が約 $0.16、続きを書かせる reply が約 $0.06。結果ファイルの末尾に実費が出ます。
ブリーフに入れる一文
「褒めなくていい。反対と穴の指摘に字数を使え」。これが無いと当たり障りのない要約が返ってきます。
Grok の数字は突合してから使う

Grok が返す再生数や市場データは Web 検索由来です。企画判断に使う前に、自分のチャンネルの実測（yt-dlp や YouTube Studio）と突き合わせます。Grok は社内実測を持たないので、「そのタイトルはクリック詐欺」と評価した企画が実際は過去最高ペースだった、ということが起きます。

06逆方向: Codex に Claude を参加させる

ディレクターを Codex にする場合も、考え方は同じです。Claude Code の CLI は claude -p "プロンプト" で1回だけ応答を返す非対話モードがあるので、Codex からサブプロセスで呼べます。

# Codex（または任意のスクリプト）から Claude にレビューを頼む例
cat draft/script.txt | claude -p "この台本を、企画意図とのズレ・冒頭30秒の4点セット・言い過ぎの3点でレビューして。修正案は該当文だけ" > _gen/claude_review.md

Codex 側の AGENTS.md に「最終レビューは claude -p に投げる」と書いておけば、毎回指示しなくても回ります。Gemini・Grok のスクリプトは Codex からもそのまま使えます。

07相談と執筆の回し方

企画段階（GPT × Grok × ディレクター）

  1. ディレクターが共通ブリーフを1本書く。企画案・チャンネル前提・聞きたいこと。数値の転記ミスに注意（221k を「221万」と書いた事故で相手の分析が丸ごとズレた）。
  2. R1: 同じブリーフを GPT と Grok に 並列 で投入する。片方の結論を見せてから聞くと引きずられます。
  3. ディレクターが両者を突合し、決定メモ v1（採用／部分採用／不採用／本人判断が必要）を書く。
  4. R2: 決定メモ v1 を両者に reply で返して叩かせる。目的は「決まった案を壊させる」こと。このラウンドが一番効きます。
  5. 必要なら GPT に R3 で反証耐性（主要な反論と先回りの応答方針）。
  6. ディレクターが決定メモを確定して本人へ。

台本段階（Gemini × ディレクター）

  1. ディレクターが章ごとにブリーフ（企画・語り手・章の位置・素材と順序・断定ライン・タグ形式・1行1文）。数値縛りは入れない。
  2. Gemini が章本文を書く（gemini_chat.py -f briefs/chN.md --system references/japanese_style.md）。
  3. qa_script.py で検査 → FAIL は ja_style_fix.py で該当文だけ Gemini に直させる。
  4. ディレクターが最終レビュー（企画とのズレ・フックの強さ・素材の位置・機械が消した対比の復元）。書き直しは Gemini に該当文だけ依頼する。
  5. qa_script.py <project> --strict が PASS したものだけ納品。修正したら取り直す。
やりたいこと誰にコマンド
企画案の科学的な言い過ぎを検出GPTgpt_consult.py ask
そのテーマの既出本数と反応を実測Grokgrok_consult.py research --search both
決定メモを壊させるGPT Grok… reply -f decision_v1.md
章本文を書くGeminigemini_chat.py -f briefs/chN.md --system references/japanese_style.md
指摘された文だけ直すGeminija_style_fix.py script.txt --strict
企画の採否・タイトル・最終レビューディレクターチャットで判断
